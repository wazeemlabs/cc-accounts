# How cc-accounts works

This is what cca does, what it writes, and which parts of Claude Code it depends on. Read it before changing cca, or when an update to Claude Code breaks something.

## Accounts are config directories

Claude Code reads its login, its global config and its conversations from one directory: `~/.claude` by default, or the directory named by the `CLAUDE_CONFIG_DIR` environment variable. Each account in cc-accounts is one such directory. `~/.claude-shared/accounts/accounts.tsv` lists them, one `name<TAB>directory` per line.

The account in `~/.claude` is special. Claude Code runs it with `CLAUDE_CONFIG_DIR` unset, and cca does the same. Setting the variable, even to `~/.claude` itself, makes Claude Code look for a credential of its own (on macOS a keychain entry named after a hash of the path), so the account would read as signed out. Its global config is `~/.claude.json`; every other account's is `<directory>/.claude.json`.

## What is shared, and how

`cca init` moves four folders out of `~/.claude` into `~/.claude-shared` and links them back: `projects` (the conversations), `todos`, `file-history` and `sessions` (the list of running sessions, which lets sessions on different accounts find and message each other). `cca add` links the same four into each new account's directory.

`cca add` also links the items named in `~/.claude-shared/accounts/share.conf` from `~/.claude` into the new account, so all accounts use one `settings.json` and one `CLAUDE.md`. Anything already at a link's place is kept beside it as `<name>.bak-<time>`. Claude Code writes `settings.json` through the link (checked: a settings write keeps the link). Plugins follow from it: `enabledPlugins` is in `settings.json`, and Claude Code installs every plugin it enables when it starts, on each account.

Not everything can be a link. Claude Code refuses to prune `history.jsonl` when it is not a regular file, so prompt history stays per account. `plansDirectory` must be inside the project, so plan files stay per account too; a resumed conversation still holds its plan.

## Auto memory and the shared folder

Auto memory lives in the conversations folder (`<config>/projects/<project>/memory/`), which every account reaches through its `projects` link. Claude Code lets a memory write through without asking only when the file's real path starts with the memory folder's path as configured. Through the link the two never match (`~/.claude-shared/projects/...` against `~/.claude/projects/...`), and the folder is inside the protected `~/.claude`, so every memory write asked for permission, or was refused in a headless run.

cca sets `CLAUDE_CODE_REMOTE_MEMORY_DIR` to `~/.claude-shared` for every session. Claude Code then names the memory folder by its real path, `~/.claude-shared/projects/<project>/memory/`, the same folder as before, and memory writes go through. The variable also moves agent memory: a `user` agent's to `~/.claude-shared/agent-memory/`, shared by every account, and a `local` one's from `<project>/.claude/agent-memory-local/` to `~/.claude-shared/projects/<project>/agent-memory-local/`.

## Choosing the account for a run

`cca run` (what `claude` runs after setup) picks an account in this order:

1. With `--resume <id>`, the account that conversation last ran on. The plugin records it in `~/.claude-shared/accounts/by-session/<id>` each time a session starts. Records untouched for 180 days are deleted at the next launch, and those conversations open on the default.
2. `CLAUDE_ACCOUNT`, when set. cca sets it for every session it starts, so a `claude` run inside a session (by a tool or a script) stays on that session's account.
3. Where the plugin last said a new session should start, from `~/.claude-shared/accounts/start`, while that is under an hour old, newer than the default and names an account in the table. The plugin writes it at the end of every session's turns and on `/account`. It names the account a planned move would take below the take thresholds (70% of five hours, 97% of the week), the default winning among accounts whose weeks reset at the same moment; then the one a stopped turn would take; and the default when none has room (`startAccount` in `usage.ts`). A default set after it (`cca use`, `/account default`) wins until the plugin chooses again. With `CCA_BALANCE=off` the plugin writes nothing.
4. The default, from `~/.claude-shared/accounts/default` (`cca use`).

`cca <name>` skips the choice and runs on `<name>`.

Whichever account it picks, cca unsets the login variables a host leaves behind (`CLAUDE_CODE_OAUTH_TOKEN` and the variables naming that login, listed in `apply` in `bin/cca`). The Claude desktop app signs a session in with its own token, every command the session runs inherits it, and Claude Code uses that token over the account's own login, so a `claude` started from a desktop session would otherwise run on the app's account under another account's name.

## Sessions the desktop app starts

The Claude desktop app starts Claude Code itself, not through cca, from a standby folder and with no `CLAUDE_CONFIG_DIR`, and signs the session in with the account the app is signed in to: it passes that login's token and names the account in `CLAUDE_CODE_ACCOUNT_UUID` (with `CLAUDE_CODE_ENTRYPOINT=claude-desktop`). The plugin takes the session's account to be the one whose login record (`oauthAccount.accountUuid` in its `.claude.json`) has that id (`hostLogin` in `context.ts`), not the config dir's, so its readings, spend and calibration count on the account that served them. Claude Code writes the login it runs on into its own config dir's record, so a desktop session leaves the app's login in `~/.claude.json`, the record of the account kept in `~/.claude`. That record therefore names the account only when no other account holds the same login (`hostAccount` in `accounts.ts`); two other accounts that both hold it name neither. On 2026-11-16 `~/.claude.json` named the app's login, the first of the two matching accounts in the table won, and desktop sessions saved the app account's readings under `~/.claude`'s account, whose week was full: the balancer moved sessions there and they were moved straight back. A login no account in the table holds is an account cca does not know: the session saves no reading and records no account. The app has a launcher setting (`CLAUDE_CODE_PROCESS_WRAPPER`), but honours it only for organizations on a third-party provider, so cca cannot start or reopen a desktop session, and the balancer cannot move one (below).

## Moving a conversation in a terminal

cca does not replace itself with Claude Code. It starts Claude Code as a child and waits, with three variables set: `CLAUDE_ACCOUNT_SWITCH_FILE` (a file under `~/.claude-shared/accounts/switch/`), `CCA_MODE=terminal`, and `CCA_PID`, cca's own pid.

`/account <name>` checks that `CCA_PID` is the pid of its process's parent, so a `claude` started inside the session (which inherits the variables) cannot act for it. When the switch is due (see [Waiting for the session's work](#waiting-for-the-sessions-work)), it writes `<name> <conversation id>` to the switch file and runs `/exit`. A command cannot run another command from inside itself, so the plugin runs `/exit` from a zero-delay timer, which Claude Code queues until the `/account` command has finished.

When Claude Code exits, cca reads the switch file. If it holds a request, cca starts Claude Code again on the named account with `--resume <id>` and the options of the first run. `libexec/cca-keep-args` decides which options to keep: it reads each option's arity from `claude --help` (a flag, one value, an optional value, or several values), drops the prompt and the options that pick a conversation or start something a second run must not repeat, and prints what it dropped. An option `claude --help` does not list is dropped too, because its value cannot be told apart from a prompt.

## Moving a conversation in VS Code

The Claude Code extension starts Claude Code itself. Setup sets `claudeCode.claudeProcessWrapper` to cca. The setting is machine-scoped: a desktop window reads it from the editor's user settings, and a remote window (WSL, SSH) from the editor server's machine settings on the remote machine. Setup writes it in both places for every VS Code family editor set up on the machine it runs on. The extension then runs `cca <its own claude binary> <args>` and talks to that process in stream-json over its stdin and stdout.

For a session the panel talks to in stream-json (the arguments begin with an option and include `--input-format stream-json`), cca replaces itself with `libexec/cca-stream`, which keeps the pid the extension knows. Any other run of the wrapper, such as `cca <binary> --resume <id>` typed in a terminal, runs Claude Code itself. cca-stream starts `cca <binary> <args>` again as its child, with `CCA_STREAM_CHILD=1`, `CCA_STREAM_PID` set to its own pid, and `CLAUDE_ACCOUNT_SWITCH_FILE` set to `~/.claude-shared/accounts/switch/<its pid>`. That run of cca picks the account as above, syncs it, and replaces itself with Claude Code (`exec`), with `CCA_MODE=stream` and `CCA_PID` set to its own pid. cca-stream passes the panel's lines to the child and the child's lines to the panel.

`/account <name>` checks that `CCA_PID` is its own process, records `<name>` for the conversation and, when the switch is due, writes `<name> <conversation id>` to the switch file and ends its own process from a zero-delay timer. In this mode SIGINT ends an idle Claude Code with exit status 0. A session in the middle of a turn reads its first SIGINT as "stop the turn" and keeps running. The switch waits for the turn to end, so this happens only to a forced switch or to a turn that a queued message starts between the check and the signal; for those the hook waits up to three seconds for the exit, sends SIGINT again, and sends SIGTERM last. When the first SIGINT cut short a turn that a queued message started, and the switch was not forced, the hook rewrites the switch file before the second signal so that the follow-up tells the conversation the move interrupted its turn and to carry on. A process that survives all three is reported in the session log with the advice to close the tab and reopen the conversation; the hook then removes the switch file and sends cca-stream SIGUSR1, and cca-stream passes what it held to the process still running.

When the child exits, cca-stream reads the switch file. With a request in it, and the panel's stdin still open, it starts a new child with the first run's arguments less the ones that choose a conversation or a point in it (`CONVERSATION` in `libexec/cca-keep-args`, the list a terminal relaunch drops too) and with `--resume <id>`. It keeps every other option, the hidden ones the panel passes included; cca opens it on the account recorded for the conversation. Before anything else the new child gets the panel's session setup again: the `initialize` control request and the latest request of each kind that sets session state (`set_*`, and `ui_attach` until a `ui_detach`), each with a fresh `cca-replay-<n>` id. cca-stream drops the child's answers to those, because the panel already had its own. No control request is left open across the switch, because the panel's SDK waits for the answer to each until the session closes, and cca-stream keeps it from closing. A setting the old child never answered is replayed under the panel's own id, so the panel gets the new child's answer. An interrupt it never answered is answered for it, since ending the process ended the turn. Any other open request of the panel's goes to the new child after the setup. A question the old child asked the panel and got no answer to, such as a permission prompt, is withdrawn with `control_cancel_request`. Then, when the switch file has lines after the first, it sends them as a user message (the follow-up). Next come the user messages the old child was sent but never took into the conversation, and last whatever the panel sent while no child could take it. Once a switch file exists, the panel's new lines are held for the next child rather than written to one about to end. The panel passes `--replay-user-messages`, so Claude Code echoes each user message, with the uuid the panel gave it, when it takes it into a turn, a message queued mid-turn included. A message with no echo when the child exits never reached the conversation, so it is sent again. Once the next child starts, output from the old one is dropped, so a process the old child left holding its stdout cannot interleave lines with the new child's. Without a request, or after SIGTERM or SIGHUP, cca-stream exits with the child's status. It forwards SIGINT, SIGTERM and SIGHUP to the child.

A process the extension started before cca-stream existed has no switch file. `/account` then ends it as before, and the panel starts a new process at the next message, which cca opens on the recorded account.

### What the panel keeps after a move

The extension reads a great deal from the process it starts, and only once: the `initialize` answer carries the account and organization it shows, the plan's models, the commands, agents and output styles, and the process's pid; it starts Remote Control itself when the setting asks for it (a `remote_control` request) and tracks its state. Nothing a process sends later updates the account. A child cca-stream starts behind its back gets none of that: cca-stream drops the replayed `initialize` answer. So after a move the panel still shows the account it was opened on until the tab is reopened. The plugin's status line names the account the process runs on.

Remote Control needs more, because a bridge belongs to the account of the process that opened it and ends with that process. Until 0.16.0 a move left the panel showing Remote Control as connected while the new process ran no bridge, so the session could not be reached from claude.ai or the phone. The panel keeps the bridge epoch from its `remote_control` answer, and afterwards marks Remote Control off only on a `bridge_state` system line of `failed` or `policy_disabled` that names that epoch. cca-stream follows the panel's `remote_control` requests and their answers (`RemoteControl` in `cca-stream-lines`). When the panel holds it on and has no request of its own on the way, the new child gets `remote_control` with `enabled` and the session name, under a `cca-replay-` id whose answer is dropped. The old bridge session's `reattach_session_id`, `work_secret` and `keep_session_on_exit` are left out, since the new account cannot take that session over. The new bridge's `bridge_state` lines reach the panel under the epoch the panel knows, so a later failure shows there. A child that refuses gets the panel a `failed` line instead, and the panel shows Remote Control off. The panel's link still points at the old bridge session, since only the answer to its own request sets it: the new session is in claude.ai's session list for the account the session moved to, and turning Remote Control off and on in the panel, or reopening the tab, shows its link. A terminal session reopens with `claude --resume` and starts Remote Control when the shared `remoteControlAtStartup` setting asks for it; one turned on by hand with `/remote-control` is not turned on again.

0.14.0 ended the process after a move instead, so the extension would start the conversation again at the next message with its whole startup. The extension shows a conversation whose process ended as stopped until that message, so sessions looked idle or disconnected right after finishing a turn; a relaunched process ended at its first turn end with no background work, which could come hours after the move. Every move is a relaunch now. cca-stream still reads a switch file whose line one ends in `fresh`, which a 0.14.0 plugin may write, and relaunches it like any other, and it removes the `CCA_STREAM_FRESH` and `CCA_STREAM_RESUMED` that a 0.14.0 cca-stream gave its children from the environment of its own.

## Waiting for the session's work

Ending the process, in either mode, stops the turn in flight and everything the session runs in the background: subagents, Monitor watches, background shell commands and workflows. A stopped tool call never writes its result, and a stopped subagent has to be resumed by hand. So `/account <name>` records the target account for the conversation at once, so the conversation opens there however this process ends, but queues the switch while there is work to wait for, and replies with what it waits for. `/account <name> now` does not wait; `/account <current account>` drops a queued switch.

What the plugin knows, and from where:

- A turn in flight: the module's `turn.start` and `turn.complete` hooks for the main loop (no `agentId`). Slash commands reach the plugin between turns in both modes (a stream-json session queues a command sent mid-turn until the turn ends), so this mostly covers a turn that a queued message starts right after `/account`.
- Background work: Claude Code's Stop hook input carries `background_tasks`, the session's work still in flight when a main-loop turn ends (subagents, shells, monitors, workflows, each with id, type and description). A hooks module cannot read it reliably: its own `classic.Stop` hook is skipped wherever the built-in `cc-plugin-sec-default` plugin is seated (Team and Enterprise organizations, managed settings), which sends classic events on past every installed plugin. The plugin's `hooks.json` therefore also declares an ordinary command hook on Stop, `plugin/hooks/record-tasks.py`, which Claude Code runs either way. It writes `{"tasks": [...]}` to `~/.claude-shared/accounts/background/<conversation id>`, and the module reads that file in `turn.complete`, which runs after the Stop hooks.
- A turn that ends without Stop (interrupted, or an API error such as a usage limit) leaves the file as `turn.start` marked it, `{"turn": "<turn id>"}`. The module then keeps what it knew, plus the work started since: it reads the tool calls it sees (a Bash result's `backgroundTaskId`, a Monitor's `taskId`, an Agent call's `async_launched`, a Workflow's `taskId`), and checks subagents against `$.agent.list()` at each decision.

Every finished background task wakes the session with a notification, as a turn of its own or inside the running one, so a turn's end follows each change, and at that end the module carries out a queued switch once nothing is left. A task stopped in a way that sends no notification keeps the switch queued until the next turn ends; `/account <name> now` switches anyway.

## Staying under the usage limits

Each response Claude Code receives on a subscription carries the account's rate-limit windows, which the plugin API passes to a `session.measure` hook whenever a window moves a whole point (`rateLimits`: each window's kind, `percentUsed` and `resetsAt`). The plugin writes them to `~/.claude-shared/accounts/usage/<account>.json`, so every session can read the readings of the accounts it is not on. A window whose `resetsAt` has passed reads as 0; one without a reset time stops counting a whole window (five hours, seven days) after the reading.

At the end of each main-loop turn, `balance.ts` reads the session's own windows (`$.session.usage()`). When the five-hour window is at 90% or more, or the weekly one at 99%, it lists the candidates: every signed-in account but this one, with its reading and the load of the working sessions on it (each live session's project weight, 1 unless set; a session idle for 30 minutes or more by its registry status counts for nothing). Those come from Claude Code's session list in `~/.claude-shared/sessions` (one `ps` call for which pids still run) and each session's `by-session` record. A candidate needs both windows below 70% and 97%. A candidate whose five-hour percentage plus 10 points per unit of load stays below that bar has room (`hasRoom`; an unmeasured account has none known) and comes before any that has none. Among those, the one whose week resets first wins, since a week's unused room is lost at its reset (an account with no known reset comes last); among weeks that reset at the same moment, the one with the lowest five-hour percentage plus the load count wins, so sessions leaving one account at once spread out. With neither window pressing, a session also makes a planned move to a candidate under the take thresholds whose week resets at least six hours before its own (`soonerTarget`), so the room of the week that resets first is spent first; a candidate with no known reset or no room never draws one. It also moves, planned, when its own account's five-hour percentage plus the load count, itself included, reaches 90%, to a candidate with room (`spreadTarget`): the balancer runs only at a turn's end, and sessions crowded onto one account fill its five-hour window within one long turn. These numbers are `POLICY` in `usage.ts`. The move is a `/account` switch, through the same code: recorded at once, carried out when the turn and background work are done. Background work can run for hours, and the readings that called for the move change meanwhile (2026-11-17: a move queued to spend a week before its reset still waited after the reset). So while a move the balancer queued waits, each turn's end plans again, counting this session on the account it runs on rather than on the target already recorded for it (`liveHere`): the same target keeps the move waiting, another target replaces it, and no move drops it and records the conversation back on its account (`dropSwitch`, which `/account <current account>` uses too). The pending switch records who asked (`by`); a person's switch is never planned again, and one an older plugin saved before a reload counts as a person's. A turn the account stops while a switch waits (the balancer's or the person's) forces that switch, to its own target, stopping the work (`hurry`): the work cannot go on on a spent account, and a session holding long background waits would otherwise stay there through every message. A planned move is not made when the full window resets within 15 minutes. The prompt cache belongs to the organization, so a move makes the new account read the whole conversation uncached, and a limit hit in those minutes still moves at once.

A turn that ended on an API error was stopped by its account when a window reads 99% or more, or when Claude Code classified the error as the account's: `rate_limit`, `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `verification_required` or `billing_error`. The classification is the `error` field of the API-error row Claude Code appends to the transcript before the turn completes, the word the StopFailure hook carries; the module reads the last megabyte of the transcript, because StopFailure hooks run only after `turn.complete`. It reads bytes, not lines: Claude Code writes up to a dozen rows after the error row as a turn ends, and the row before it can be megabytes (a screenshot). It catches what the readings miss: a per-model limit (a model's weekly cap, which no window shows) and a lost login on an account the session just moved to, which has no reading yet. Such a move does not wait (the work would only fail on this account). It takes any account below the leave thresholds, because any room is better than a stopped session, and its switch file carries a follow-up: the conversation is told which account stopped it and which it now runs on, to carry on, and which background tasks the move stopped. A failure the readings do not explain is written to `blocked/<account>/<scope>.json`, and for a while no session it would stop moves onto that account, so sessions cannot bounce between two accounts that both hit a per-model limit. A usage limit can clear at any time, so the account is tried again after an hour. A refusal does not clear on its own, so the account is tried again after a day (`blockMsOf` in `usage.ts`). Refusals are a lost login, an organization that turned off Claude Code on its subscription (`oauth_org_not_allowed`), a hold or a billing failure. An account whose plan has ended is better removed with `cca remove`. A usage limit with no window at its limit is a per-model one (the API's code for it is `model_requires_usage_credits`: the plan's included use of that model is spent), so its scope is the model family that hit it: `fable`, `opus`, `sonnet`, as `familyOf` in `failures.ts` reads them from a model id (`claude-opus-4-6`) or alias (`opus[1m]`). The family is the session's model setting (`$.config.list()`), or, when that names no one family (`default`, `best`, `opusplan`), the model that last answered in the process. Sessions on other families still move to that account. A lost login, a hold or a billing failure has the scope `account`, as does a limit whose family is unknown, and holds back every session. A limit the readings show gets no record: they show it to every session, with its reset time. When the transcript cannot be read, the readings alone decide.

Projects can be weighted (`priorities.ts`). `priorities.json` maps a folder to a weight above 0 and at most 100. A session's project is the folder it works in (`$.session.root()`, also in its session-list entry). That is where it started, or where the desktop app moved it: the app starts a session in a standby folder under `~/.claude/spares` and moves it to the folder the person picked, so `session.start`'s `cwd` would name the standby folder, and it takes the weight of the nearest folder at or above it, else 1. The candidates' load is the summed weight of the live sessions on them, divided by the plan size in Max 5x plans. The plan size is read from the login record's rate-limit tier (`default_claude_max_5x` is 1, `default_claude_max_20x` 4, Pro a fifth, an unknown tier 1). The score is the five-hour percentage plus 10 points per unit of load. Once the session's own account passes `yieldAt` (75% of five hours, 95% of the week), a session whose project outweighs nobody else's stays, but one sharing the account with a heavier session makes a planned move. That move needs a target under the take thresholds; with none, the session stays without a log line, because making room is a courtesy.

Budgets (`budgets.ts`) hold each project to a daily allowance. `budgets.json` maps a folder to points a day, a point being one percent of a Max 5x week. At each main-loop turn's end the plugin adds the turn's cost (`turn.complete`'s `usage`: the four token counts and the model, weighted as `FAMILY_WEIGHTS` and the cache and output ratios in `spend.ts` say) to `spend/<UTC day>/<conversation id>.json`, which only that session writes, under the folder it works in at that turn (`{"folders": {...}}`: a session that moves folders keeps each folder's spend there; the one-folder records of 0.13 and earlier are read as one folder). At each `session.measure` it also adds the weekly window's rise since the last reading to `calibration/<day>/<account>.json` (only a reading whose week resets at least a day later than the one recorded starts a new week and counts from zero; one whose week reset at least a day earlier, a session's late view of last week, adds nothing; a lower reading of the same week is another session's older view and adds nothing, the next rise counting from the highest; two sessions of one account measuring at once can lose an increment, which counts spend low, never high). Tokens per point is every session's tokens over every account's consumption across the last three days, once ten points have been consumed; before that, seven million. A client's record counts in it only on a day its account has a calibration record: an account only a client used reports no readings, so its tokens would have no points beside them and every point would read larger than it is. The day's supply is each signed-in account's room below the weekly leave line spread until its reset, plus a fresh week's share after it (a seventh of 99 points per Max 5x unit, also assumed for an account with no reading). A budgeted project's allowance is its budget; the projects without one that have a live session share the supply left after the budgets, by their weights. A project is over budget when its spend today reaches its allowance times the fraction of the day elapsed plus a quarter. Then `register.ts` parks the session: it decides at the turn's end, so a turn in flight is never cut, refuses every `tool.call` with the figures and when the day turns, and checks again at each refused call. A refused session goes idle, and nothing of its own would start it again, so `parking.ts` wakes it: the first refusal writes `parked/<conversation id>` with the folder it works in and starts a check every `WAKE_MS` (a minute), and `wakeParked` runs from that check, at every main-loop turn end of any session, and after `/account budget` or `priority` writes. For each record whose project `overrunsNow` no longer finds over, the waker removes the record with a plain `rm`, which only one remover can do, so a session is woken once; it submits the carry-on prompt (`wakeText`) with `$.prompt.submit` from a zero timer when the record is its own (the engine refuses a submit from a `command.run` hook), else sends it with `$.session.send`, putting the record back when it was not delivered. Other sessions' turn ends reach a session whose plugin reloaded, which loses its timer. A record of a session no longer in Claude Code's running session list (`runningSessions`) is removed. A session that goes on (a call that runs unparked, or a new main-loop turn, which a person or a wake started) removes its record and stops its check, so it is not prompted after the fact; a refusal in that turn writes the record again. The turn the refusal came in does not count: a budget raised before it ends still wakes the session. Sessions the desktop app opens without a folder start in scratch folders under `scratchRoot` (`~/Library/Application Support/Claude/scratch-workspaces`); while the file holds any budget, `budgetsInForce` adds `SCRATCH_BUDGET` (5 points) for that folder unless the file names it, so they are one project with an allowance rather than projects sharing a remainder that is zero once the budgets set exceed the supply. With no budget set nothing is parked; `CCA_BUDGET=off` turns parking off and the counting stays. A client outside Claude Code (an LLM bridge signed in to one of the accounts) records each call with `cca spend`: `bin/cca` resolves `--account` to an account by its name or the email its config is signed in as, and `libexec/cca-spend` adds the call's four raw counts under its model to `spend/<UTC day>/client-<account>-<first 12 hex of the project's SHA-256>.json`, holding an exclusive `flock` on the record's `.lock` file and replacing it atomically, since a bridge's calls run in parallel. `parseSpend` weighs a record's `usage` per model with `weightedTokens` as it reads the day, so a token's cost stays defined in one place, and the record counts in its project's budget and in calibration like a session's.

Transcripts are pruned (`prune.ts`, `hooks/prune.py`). Claude Code's loader ignores the request log rows (`api-request`, `api-request-shape`, `api-request-blob`) when it rebuilds a conversation; they are a request-replay record, and a process that starts reads which blobs exist from the file again. So a transcript idle for an hour (`IDLE_SECONDS`, the prompt cache's life, counted from its newest row's own `timestamp`, since a prune's rewrite changes the file's mtime; from the mtime only when no row has one) loses its whole request log, compacted or not, for a saving of 64 KB or more (`MIN_IDLE_SAVING`: it is rewritten once, and the state then passes it by); a 9 MB conversation that lost its 380 log rows resumed with the same first and last messages. A fork (`fork-context-ref`, in the conversation's own transcript or its subagents') names the message it started from, which Claude Code reads back with its parents to rebuild the fork; those are kept like the rows after the boundary. `prune-state.json` records the rules' version (`STATE_VERSION`), and a state of other rules looks at every transcript again. At `session.start` the plugin spawns `prune.py --all`, and after a `session.compact` that was not skipped or only precomputed, at the main loop's next turn end, `prune.py --session <id>`, which covers the conversation's subagents too; the session never waits on the child, and `prune()` reports a failure in the transcript and never rejects. `prune.py` takes one machine-wide `flock` on `prune.lock` and, with `--all`, looks only at transcripts of 64 KB or more (`MIN_IDLE_SAVING`: a smaller one cannot save enough) whose size and mtime differ from `prune-state.json`, which records a transcript only once it was idle when looked at, so one still active is looked at again until its request log can go. In a transcript it finds the last compact boundary of the main loop (`system`/`compact_boundary`, not a sidechain) and drops the conversation rows (`user`, `assistant`, `attachment`, `system`, `progress`) before it, except the uuids the boundary's `compactMetadata` names (its preserved messages) and any row a row after the boundary names as its parent, with that row's parents. In a transcript active within the hour the request log is cut back the same way. It is delta-coded: an `api-request` starts with the first `keep` messages of the request before it and adds its `tail` of blob hashes. So it keeps every request after the boundary and the chain they build on, walking back while `keep` is above 0 both in file order and within each `querySource`, and every request a kept one names as its `base` (the one it starts from, whatever its query source), and drops older requests and the `api-request-blob` and `api-request-shape` rows no kept request names. Then every base64 image in the kept conversation rows but the newest five (`KEEP_IMAGES`) becomes a text block saying it was removed; blobs are never edited, since their hash names them. A row's `toolUseResult` is the tool's own copy of what it returned, which the API never sees: a Read of an image keeps the image again in `file.base64` (311 MB in the 60 largest transcripts on 2026-11-15). It does not count among the newest five, and once its row shows none of its images it loses its own: a Read result's `base64` becomes empty, as Claude Code's own slim mode for remote sessions writes it, and any image block in it becomes the same text block. Every other row stays where it was. A transcript active within the hour saving under 1 MB (`MIN_SAVING`) is left alone, so a live one is not rewritten for a few rows. If a live but idle session goes on, its process still holds its own list of the blobs it wrote and does not write those again, so requests after the prune can name blobs the file no longer has; the conversation does not depend on them. The new file is written beside the old, keeps its mode and replaces it atomically; rows appended since the scan are copied over before the replace, and rows a writer put into the old file after it, read through the still open old file, after it. Claude Code opens a transcript for each row it appends, so a live one can be pruned; a row written in the instant between that last copy and the replace may land after a newer one. Claude Code also rewrites a transcript itself: its own compaction renames a new file over the path (`performCompactTranscript`), and removing a row truncates the file in place and writes the rows after it back (`performRemoveByUuid`). A copy of the old bytes would lose the rows written to the new file, or bring back a removed row and garble the next. So before the replace the prune checks, as Claude Code's own rewriter does, that the path is still the file it opened, no shorter than what it copied, and with the bytes it scanned unchanged at three places, and that every row it copied was read whole; otherwise it leaves the transcript as the other writer made it and looks at it again on the next run. A row nested deeper than Python's recursion limit leaves that transcript as it is, reported once, and the others are still pruned. A SIGTERM, as a hot reload of the plugin sends its children, removes the temporary file and leaves the transcript as it was; `prune()` writes that to the debug log, not as a failure.

`/account usage` (`report.ts`) reads every account's reading, plan size and failure records, and every live session with its folder. It shows each account's free five-hour and weekly room with the time until each resets. It totals the free room, in Max 5x plans, over the accounts that can serve a session now: signed in, measured, no window spent and no hold on the whole account. It also totals the room left before sessions move off (the leave thresholds). Last it lists the projects by weight, with their sessions and accounts. `/account` ends with the first total. `survey.ts` holds the readings, plan sizes and live sessions that the report and the balancer both read.

Scheduled wakeups need nothing from cc-accounts. Claude Code rebuilds the session's own (`durable: false`) from the transcript when the conversation is resumed, with their ids, and every switch reopens the conversation with `--resume`. Up to 0.5.1 the follow-up listed them and asked the conversation to set them again, which doubled each one. The follow-up now only says why a turn stopped or was cut. A terminal relaunch passes it as the first prompt; cca-stream sends it as a user message. An account no session has reported on is taken only when no reported account has room; a session that moves there reads the truth at its first response and moves again at the next turn's end if it must. When no account has room, the session stays and logs why. A session nothing would reopen elsewhere, one the desktop app started or one cca did not start, stays too: when it would leave (a stopped turn, or a window at the leave line not about to reset) it says once per full window, in its log and status line, why it cannot move, which account a move would take, and how to go on there (`stranded` in `balance.ts`). It records no failure, since the login that failed may be the host's rather than the account's in cca. `CCA_BALANCE=off` stops the moves; the readings are still written.

## Folder trust and MCP servers

Each account's `.claude.json` holds settings that cannot be linked, because the file also holds the account's login. Before every session starts, in a terminal and in VS Code, `libexec/cca-sync` gives the starting account what all accounts share:

- Folder trust: `projects[<path>].hasTrustDialogAccepted`. Claude Code treats a folder as trusted when it, or a folder above it up to the git repository's root, has that flag. A run without a terminal, as VS Code's are, does not ask: without the flag it skips what needs trust, such as an MCP server's `headersHelper` and the MCP servers and hooks an agent definition brings. Each account gets the union of all accounts' trust. Trust is only added, never removed.
- Per-project MCP settings: a project's local servers (`projects[<path>].mcpServers`) and the answers about its `.mcp.json` servers (`projects[<path>].enabledMcpjsonServers` and `disabledMcpjsonServers`). One added, changed or removed on any account is added, changed or removed on all of them.

`~/.claude.json` holds the shared copy of these. A change on another account has to be told apart from a copy that account has not caught up on, so `~/.claude-shared/accounts/sync-state.json` keeps, per account, a digest of each item as cca last saw it there. It holds digests only, never a server's command, URL or secrets. At each start, cca-sync applies every account's changes since its last sighting to the shared copy, then makes the starting account match it. An account seen for the first time adds what it has without replacing what is already shared. When two accounts change the same item, the starting account's change wins. `CCA_TRUST_SYNC=off` and `CCA_MCP_SYNC=off` turn each part off.

Running sessions write `.claude.json` often, so cca-sync writes the way Claude Code does:

- It takes Claude Code's lock on the shared copy and on the starting account's config: the directory `<config>.lock`, created with `mkdir` (the `proper-lockfile` convention). If a running session holds a lock for 3 seconds, cca-sync gives up, says so, and tries again at the next start. It never breaks a lock. One cca-sync runs at a time, under an OS lock on `sync-state.json.lock`.
- Under the lock it reads the file again, makes the change, writes a temporary file with the original permissions, syncs it to disk and renames it over the config.

Claude Code saves `.claude.json` by applying its change to a fresh read taken under the same lock, so a running session keeps what cca-sync added. It picks up new MCP servers at its next start.

A folder the account has never opened needs a new entry. Claude Code reads an entry as written, without filling in defaults, so a new entry must have every field Claude Code's own default entry has. cca-sync reads that default from the installed Claude Code binary (it is a literal, `{allowedTools:[],mcpContextUris:[],...,hasTrustDialogAccepted:!1,...}`), checks it holds only empty lists, empty objects and booleans, and caches it per binary in `~/.claude-shared/accounts/cache/`. If the literal is not there in that shape, cca-sync only changes folders the account already has entries for, and says so.

## User MCP servers in one file

User MCP servers live in `~/.claude-shared/mcp.json`, in the `{"mcpServers": {...}}` format `claude --mcp-config` reads. cca passes it to every session it starts, as `--mcp-config=<file>` before the other arguments: the option takes several values, and the `=` form leaves a prompt or subcommand after it alone. In VS Code it goes in front of the extension's own options, beside any `--mcp-config` of the extension's. The servers keep their names, so their tools are `mcp__<server>__<tool>` as before. Claude Code started some other way does not load the file.

`claude mcp add --scope user` writes to the account's `.claude.json`. At each start cca-sync moves every user server the starting account and `~/.claude.json` hold into the file and leaves those two configs holding none; it also takes in servers added or changed on the other accounts, which are emptied when they start. A server cca saw on an account before and that is unchanged there is a stale copy: it is not taken back into the file, so an edit or removal made in the file stands. The file is written before the configs lose their copies, created private (0600, it holds the servers' secrets), and never rewritten when it does not parse: then every server stays where it is until it is fixed. `CCA_MCP_SYNC=off` stops the moving; the file is still loaded.

## The plugin

`plugin/` is a Claude Code plugin, loaded in every session through `CLAUDE_CODE_PLUGIN_DIRS` in the env block of `~/.claude/settings.json` (which every account shares). `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` beside it makes Claude Code watch the plugin's folder in every session: a terminal session watches it by default, but a headless one (the desktop app, an SDK client) does not, and without the watch an update reached such a session only through `/reload-plugins` or a restart. With it, a session reloads the changed plugin once its turn ends, running `session.start` again, so the plugin's state is rebuilt. `cca init` sets it, keeping a value already there; `install.sh` sets it on an update where the plugin is loaded and it is not set; `cca uninstall` removes it when it is `1` and no other plugin dir is left. It registers `/account`, shows the account and its usage in the status line, records each conversation's account when a session starts, follows the session's turns and background work so that a switch can wait for them, saves its account's usage, and moves the conversation off an account that is nearly spent. It reads cca's state directory from `CCA_ROOT` and the shared directory from `CCA_SHARED`, which cca sets, or `~/.claude-shared/accounts` and `~/.claude-shared`.

## Preferences the editor saves

VS Code's Claude in Chrome and memory dialogs save their settings by running the binary once, as `claude edit-chrome-settings` or `claude edit-memory-settings`, from the extension itself rather than from a session. That run goes through the process wrapper too, but names no conversation, so nothing says which panel's account asked, and the setting lives in each account's `.claude.json`. cca runs the helper on every account, feeding each the same input, so the setting reads the same everywhere, as a shared one. Without this the setting went to the default account, and a panel on another account kept reporting it off (Claude in Chrome then never connected there). A helper run from inside a session, where `CLAUDE_ACCOUNT` is set, or with `--resume`, runs on that account alone.

## Windows

cc-accounts runs in WSL, where Claude Code is a Linux program and everything above applies. Claude Code installed natively on Windows is not supported: cca is a bash script, the shared folders are symbolic links (which need Developer Mode or administrator rights on Windows), the terminal switch and the VS Code switch rely on POSIX processes and signals, and the extension cannot run a bash script as its process wrapper. Native support needs a port of cca to Python with directory junctions, a `.cmd` wrapper, and a different way to end the VS Code session; it is tracked in issue #1.
